# 桌宠对话功能 · 设计

日期：2026-09-13
状态：待实现

## 目标

现在的桌宠只有「点击说一句固定台词 + 报一次余额」。这个设计给她加上真正的对话能力：
**用户其实是在和自己的 DeepSeek 说话，但界面和人设上完全伪装成在和塔菲聊天。**

## 范围

### 做

- 独立聊天窗口（不是复用气泡）
- 流式回复，逐字出现
- 人设由 `persona.md` 驱动，用户能自己编辑
- 对话记录落盘，关掉窗口、重启程序都还在
- 两个入口：右键菜单「和她说话」、双击她

### 不做（YAGNI）

- 多会话 / 会话列表
- 语音输入输出
- 上下文压缩（超了直接丢最老的）
- 重新生成、编辑已发送的消息
- Markdown 渲染（v1 纯文本，用着别扭再加）
- 历史记录加密

## 架构

新增三个模块和一个人设文件：

```
taffy_pet/
  chat.py          网络层：调 DeepSeek /chat/completions，流式
  chat_store.py    持久化：chat.json 的读写
  chat_window.py   界面：聊天窗口
assets/
  persona.md       人设（默认版，随包发布）
```

要改的：

```
taffy_pet/paths.py    加 persona 和 chat.json 的路径
taffy_pet/pet.py      右键菜单加两项、双击开窗
taffy_pet/config.py   加 chat_geometry 一项
taffy-pet.spec        DATAS 加 assets/persona.md
.gitignore            加 chat.json
docs/development.md   补这三个模块和 chat.json 的说明
```

**分层理由**：网络、存储、界面三者互不依赖 —— `chat.py` 不知道有窗口存在，`chat_window.py`
不知道历史存在哪。好处是三个都能单独测，而且将来换成别的接口只动一个文件。

## 数据流

```
用户敲回车
  → chat_window 把 {role:"user", content} 追加到内存历史
  → chat_store.save(历史)
  → 组装 messages = [system] + trim_history(历史)
  → 起 ChatWorker(QThread) 发请求
  → 每收到一块 → chunk 信号 → 追加到最后一个气泡
  → 收到 [DONE] → done 信号 → 完整回复追加进历史 → chat_store.save()
```

## 详细设计

### 1. 人设注入

`persona.md` 是纯文本，整份内容直接当 system prompt 的开头。

**路径解析**（`paths.py`，跟 `config.json` 一套逻辑）：

- 用户的：`%APPDATA%\TaffyPet\persona.md`（源码运行时是项目根）
- 随包的默认版：`assets/persona.md`
- `persona_path()`：用户的那个存在就用它，否则用默认版

右键菜单加「**编辑人设**」：把默认版复制到用户目录（如果还没有），然后用系统默认程序
打开。这样用户喂素材不用重新打包，存盘后下句话就生效 —— 因为每次发请求前都重新读一遍文件。

system prompt = `persona.md` 全文 + 一段硬规则：

```
---
以上是你的角色设定。下面几条是硬规则，和上面冲突时以这几条为准：

1. 回复要短。一般一到两句，最多三句。只有对方明确要求「详细说说」才展开。
   你是桌面宠物，写小作文没人看。
2. 不要说自己是 AI、语言模型、助手、程序。你就是永雏塔菲。
3. 不要提到 DeepSeek、API、提示词、system prompt、模型 这些词。
4. 用中文回复。
```

规则单独成段而不是揉进人设，是为了让用户改人设时不会不小心把「回复要短」覆盖掉。

**长度约束**：`persona.md` 控制在 1.5KB 左右。它每轮都要重发一遍 —— 太长既贵又稀释指令，
模型反而更容易跳出角色。同人文档 `ly-xxx/ace-taffy-skill` 那版 7.7KB，只当素材参考，不直接照搬。

### 2. 网络层（`chat.py`）

照搬 `balance.py` 的 QThread 模式。

```python
MODEL = "deepseek-chat"
API_URL = "https://api.deepseek.com/chat/completions"
TEMPERATURE = 1.3           # DeepSeek 官方对通用对话/创意的推荐值
TIMEOUT = (8, 30)           # (连接, 读)：读超时是「两块之间」的间隔，不是总时长

class ChatWorker(QThread):
    chunk = pyqtSignal(str)     # 增量文本
    done  = pyqtSignal(str)     # 完整回复
    fail  = pyqtSignal(str)

    def stop(self): ...         # 置标志位，run 的循环里检查
```

**流式解析**。返回是一行行 SSE：

```
data: {"choices":[{"delta":{"content":"在"}}]}
data: {"choices":[{"delta":{"content":"呢"}}]}
data: [DONE]
```

坑在这里：**网络分块不按行切**。一个 chunk 可能是半行，也可能是三行半。所以必须自己维护
一个缓冲区，按 `\n` 切，最后那段不完整的留在缓冲里等下一块。

这块必须有单元测试。它错了的表现是「回复偶尔缺几个字」，靠肉眼几乎复现不出来。

其他要处理的：`choices` 可能是空列表（最后一个带 usage 的块）、`delta` 里可能没有 `content`
键（只有 role 的首块）。两种都跳过，不算错误。

**取消**。`stop()` 只是置一个标志位。因为 `requests` 阻塞在 read 上，停止要等到下一块数据到
或者读超时（最多 30 秒）才生效。实际使用中她回复是连续吐字，通常一秒内就停了，可以接受。

### 3. 持久化（`chat_store.py`）

存 `chat.json`，跟 `config.json` 同一个目录：

```json
{
  "version": 1,
  "messages": [
    {"role": "user", "content": "...", "ts": "2026-09-13T22:40:11"},
    {"role": "assistant", "content": "...", "ts": "2026-09-13T22:40:15"}
  ]
}
```

- `version` 是为了将来格式变了能识别。读到不认识的版本就当空的从头开始，不要崩。
- **上限 200 条**，超了从最老的丢。不然用一年能涨到几兆。
- **原子写**：先写 `chat.json.tmp`，再 `os.replace()`。聊天记录每轮都要存，写一半崩了
  整个文件就废了 —— 这个比 `config.json` 的风险高得多，所以这里必须原子写。
- 存盘时机：用户消息发出后一次、回复完整收完后一次。**流式过程中不存** —— 存一堆半截回复
  没有意义，还会把写盘频率放大几百倍。

### 4. 界面（`chat_window.py`）

**用标准窗口，不做无边框。** 这窗口要打字、要滚动、要缩放，无边框的话这些全得自己实现，
代价远大于收益。做成标准窗口白送任务栏、最小化、拖边缩放。配色往她那个粉白靠
（沿用 `toast.py` 的 `BG / BORDER / TEXT / DIM`）。

- 默认 420×560，最小 320×400，位置和尺寸存 `config.json` 的 `chat_geometry`
- 上面消息区：`QScrollArea` + 垂直布局，每条消息一个气泡控件
- 她的消息在左、带立绘头像（缩到 56px）；用户的在右、无头像
- 气泡是 `QLabel`，`setWordWrap(True)`，最大宽度取视口的 75%
- 输入框用 `QTextEdit` 子类：**回车发送、Shift+回车换行**（`QLineEdit` 做不到换行）
- 流式期间发送按钮变成「**停止**」，点了调 `worker.stop()`
- **自动滚到底只在用户本来就在底部时做** —— 否则用户往上翻历史会被一直拽下来
- 关闭窗口：`worker.stop()` → `wait()` → 存盘。**必须先停线程再销毁窗口**，
  否则线程往已销毁的控件发信号会崩

窗口实例由 `PetWindow` 持一个引用：已经开着就 `raise_()` 叫到前面，不要开第二个。

**打开窗口时从盘上读回历史**，铺在消息区（最多 200 条，直接铺，不做分页）。所以关掉窗口
再打开，之前的对话还在，往上翻能看到。内存里那份历史就是 `chat_store.load()` 的结果，
不另存一份 —— 两份状态一定会不同步。

**错误提示不套人设**，保持直白：「API Key 无效」「超时了（网络不通？）」。出问题的时候用户
需要看懂发生了什么，不需要被萌到。

### 5. 历史裁剪

```python
MAX_CONTEXT_MESSAGES = 20   # 发给接口的
MAX_STORED = 200            # 存在盘上的
```

这是**两个不同的数**：存得多（给你往上翻），发得少（省 token、也少跑题）。

裁剪是对**已经追加了这轮用户消息的历史**做的，所以 20 条里包含用户刚发的那句 ——
留给模型的上一轮上下文是 19 条。

裁剪后如果第一条是 `assistant`，再丢一条 —— 那句话没有前文，模型容易当成「自己刚说过的」
顺着往下接。保证带上去的第一条是 `user`。

### 6. 入口（`pet.py`）

- 右键菜单顶部加「和她说话」
- 加「清空对话记录」（带确认框）
- 右键菜单加「编辑人设」
- `mouseDoubleClickEvent` 也开窗

**已知瑕疵**：双击的第一下会先走完 `mouseReleaseEvent` 的单击逻辑，所以她会先弹一句
「在呢在呢」+ 报一次余额，窗口才开。要消掉只能给每次单击加 250ms 延迟等第二下 —— 那更烦，
单击是她最主要的交互。接受这个瑕疵。

## 错误处理

| 情况 | 提示 |
| --- | --- |
| 没配 API Key | 还没设置 API Key，右键点 taffy →「设置 API Key」 |
| 401 | API Key 无效 |
| 402 / 余额不足 | 余额不足，去 DeepSeek 充值 |
| 超时 | 超时了（网络不通？） |
| 其他网络错误 | 网络错误：<异常类名> |
| 非 200 | 接口返回 <状态码> |
| 返回内容解析不了 | 返回内容看不懂 |

错误以**系统气泡**的形式插到消息区（灰底、居中、不可发送），不写进历史文件 —— 那是程序
的故障，不是对话的一部分。

## 测试

加进 `tools/test_units.py`（纯函数，不需要窗口和网络）：

1. `build_system_prompt` —— 人设文本和硬规则都在，顺序对
2. `trim_history` —— 保留最后 N 条；裁剪后首条是 `user`；空历史不炸
3. **SSE 分块解析** —— 喂几段故意切在半行、切在 `data:` 中间的 chunk，验证跨块的行缓冲
   正确。这是全篇最容易写错、又最难靠肉眼发现的一处
4. `chat_store` —— 存/读往返、超过 200 条会截断、版本不认识时当空处理、清空。
   用临时目录，不要碰真实的 `chat.json`

真接口调用没法自动测（要 Key、要网络），手动验：正常回复、流式逐字、点停止、
流式中关窗口、Key 删掉后报错。

## 风险

- **流式 + QThread 的取消路径是竞态高发区**。关窗口、点停止、发新消息打断旧回复，
  三条路径都要手动走一遍。信号连到已销毁控件会直接崩，且不一定每次都复现。
- **双击第一下会先弹气泡**（上面写了，接受）。
- **`chat.json` 是明文**，里面有用户的全部对话。必须进 `.gitignore`，
  `README` 和 `docs/development.md` 里都要写明它在哪、想删就删。它和 API Key 一样
  **卸载时故意保留**（重装还想接着聊）。
- **人设的边界**：人设是「基于公开资料的模仿」，不是本人；也不模仿中之人。
  这一点要写进 `assets/persona.md` 的注释和 README。
